## Results and discussion

Beyond the coverage and centeredness metrics reported above, several aspects of Road Centerline Extractor's output are relevant to its intended use in corridor-network mapping — roads, rivers, or other elongated networks represented as polygons.

Segmentation at T-junctions and intersections produces individual features between nodes rather than a single continuous line per polygon, which is a prerequisite for per-segment classification (road class and surface type in a road network; reach or channel type in a river network) and was not automatic in any of the other three tools tested. This segmentation is a toggle rather than a fixed behaviour, since not every corridor type has junctions in the same sense a road network does — a single-thread river reach, for instance, would typically be run with it off, producing one feature per input polygon instead. Combined with configurable spur pruning — removing short branches below a minimum length, which arise as a known artefact of Voronoi-based skeletonization near irregular boundary segments — and a minimum-width filter that excludes non-corridor sections such as passing bays or local widenings, the output requires comparatively little manual editing before use. The extent to which this reduces editing time in practice has not been quantified here and would require a separate, user-facing evaluation.

Each output feature is attributed with its length, computed and converted to a unit of choice (m, km, mi, ft) at generation time, together with a reference to the source polygon feature. This is a modest addition relative to the geometric processing described above, but removes a step (field calculation) that would otherwise be needed before the output is analysis-ready.

On the single dataset tested — a forest road network — coverage of the reference network (99.8%) was substantially higher than Grass v.voronoi.skeleton (50.5%) and BecaGis Tools (Skeleton) (19.6%), both of which failed to produce output over large sections of the more topologically complex parts of the network rather than degrading gracefully. Centeredness (91.5%) matched the unprocessed, raw Voronoi skeleton (91.5% on the same data) and exceeded the other tools tested except BecaGis Tools (Skeleton), indicating that segmentation, pruning, and trimming do not measurably degrade centering accuracy relative to the underlying extraction method — though this was tested on one dataset and would benefit from replication on other polygon geometries, including non-road corridors, before being treated as a general result.

This balance between coverage and centeredness reflects a deliberate default: dead-end tips are left at the last genuine skeleton point rather than extended to touch the polygon boundary, since that point is equidistant from the polygon walls that produced it, whereas stretching it to the boundary trades that property away as the extension approaches an asymmetric corner. A separate toggle restores the boundary-extending behaviour for use cases where maximizing coverage matters more than tip-level centering accuracy. Spur pruning was also found to need a width-relative floor in addition to an absolute length threshold: a short branch near a converging tip can exceed an absolute length setting tuned for a given corridor width while still being disproportionately short relative to the local width at that point, which is the more reliable signal that it is a Voronoi artefact rather than real network structure. Neither adjustment has been benchmarked as systematically as the coverage/centeredness comparison above and both would benefit from testing on further datasets.

Two additional points are worth verifying rather than assumed. First, `v.voronoi.skeleton` is not a native GRASS tool but a QGIS-side wrapper, and has broken across GRASS7→GRASS8 transitions in past QGIS releases; Road Centerline Extractor's Python/QGIS-API implementation has no such dependency, though this has not been tested across QGIS versions here. Second, a previously reported GitHub issue describes `v.voronoi.skeleton` returning different results between the UI and `processing.run()` calls given identical parameters; whether Road Centerline Extractor is deterministic under the same conditions has not yet been explicitly verified and should be before the claim is made publicly.

Finally, none of the processing steps described above are road-specific by construction — T-junction segmentation, spur pruning, and width filtering are independent parameters layered on top of a generic polygon-skeletonization step, rather than built into it or tied to a fixed "road mode". This suggests, but does not by itself demonstrate, applicability to other elongated polygon networks such as trails or river corridors; the benchmark reported here was run on road data only, and testing on non-road datasets has not yet been performed.
